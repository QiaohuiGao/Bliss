# i18n Contributor Guide

Bliss ships **English only** today, on a real i18n layer. Adding `es` or `zh`
must be a translation job, not a refactor. That is the acceptance criterion for
this architecture, and every rule below exists to protect it.

---

## Stack

| Surface | Library | Why |
|---|---|---|
| `apps/web` (Next.js App Router) | `next-intl` | Works in Server Components, locale-segment routing, native ICU MessageFormat, typed keys |
| `apps/api` (Fastify) | `intl-messageformat` | Only needs a handful of strings; no framework required |

Both read from **`packages/i18n`**. There is exactly one source of truth for
every string in the product.

If a native client is added later, `i18next` + `i18next-icu` consumes these same
ICU catalogs, so the catalogs do not need to change.

Rejected: `react-intl` (weak RSC story), `lingui` (extra build step), raw `Intl`
alone (no plural/select, which breaks Spanish immediately).

---

## Layout

```
packages/i18n/
  src/
    config.ts                  SUPPORTED_LOCALES, fallback chain, formatters, RTL
    index.ts                   loadMessages, loadContent, translate
    locales/
      en/  common.json  onboarding.json  board.json  quest.json  errors.json  glossary.json
    content/
      en/  quests.json         base quest tree copy
           cultures.json       cultural pack copy
  scripts/
    check-parity.ts            CI gate: key sets must match across locales
    build-pseudo-locale.ts     generates en-XA for layout testing
```

**`locales/` is UI chrome. `content/` is product content that gets written into
the database.** They are separated because they have different lifecycles: UI
copy changes with screens, content copy changes with the wedding-planning
domain.

## Key naming

Keys are **namespaced and semantic**. The first segment is the namespace.

```
common.nav.dashboard              ✅
onboarding.step.budget.title      ✅
board.countdown                   ✅
quest.attire_beauty.task.order_the_gown.title    ✅

step1Title                        ❌ positional, breaks when steps reorder
btnOk                             ❌ describes the widget, not the meaning
"Save"                            ❌ English as the key
```

Content keys follow the generator's shape exactly:

```
quest.<questKey>.title | .subtitle | .celebration
quest.<questKey>.section.<sectionKey>
quest.<questKey>.task.<taskKey>.title | .description

culture.<culture>.quest.<questKey>.title | .subtitle | .celebration
culture.<culture>.section.<sectionKey>
culture.<culture>.task.<taskKey>.title | .description
```

## ICU MessageFormat

Never concatenate strings to express grammar. Plural rules differ per language,
and some languages have six forms where English has two.

```jsonc
// ✅
"countdown": "{days, plural, =0 {Today's the day!} =1 {Tomorrow!} one {# day to go} other {# days to go}}"

// ❌ — cannot be translated into Polish, Russian, or Arabic
`${days} days to go`
```

Chinese has only the `other` form. Spanish needs `one`/`other`. Arabic needs
`zero`/`one`/`two`/`few`/`many`/`other`. Writing the ICU form up front costs
nothing and makes all of that a translator's problem rather than a code change.

## What must never be translated

| Thing | Why |
|---|---|
| Enum values and option `value`s (`buy_custom`, `black_tie`, `WA`) | They reach the database. Labels are translated; values are identifiers. |
| `templateKey`, `i18nKey` | They are lookup keys. |
| User-authored content (custom quests, notes, task titles they typed) | It is their writing. `i18nKey IS NULL` marks these rows. |
| US state codes | Identifiers, not display strings. |

## Localizing database-generated content

This is the genuinely hard part, and the reason for the `i18n_key` columns.

Quest, sub-module, and task rows are **generated per wedding and then
persisted**, so their text would otherwise be frozen in whatever language the
couple onboarded in. Translating later would mean rewriting user data.

The rule:

- Template-derived rows store a stable **`i18n_key`** alongside a rendered
  `title`. **The key is the source of truth for display.** The stored title is a
  fallback and a search field.
- **User-authored rows have `i18n_key = NULL`** and are rendered verbatim,
  forever, in whatever language the couple wrote them.

On web, use `useContent()` from `lib/content.ts`, which handles both cases:

```tsx
const content = useContent()
<h3>{content(task.i18nKey, task.title)}</h3>
```

## Currency, dates, and layout

- **Currency is a property of the wedding, not of the reader.** A
  Spanish-speaking couple marrying in Texas sees `$34,200`, never `34.200 €`.
  Money is stored as integer cents and formatted with
  `Intl.NumberFormat(locale, { currency })`.
- **Dates** go through `Intl.DateTimeFormat` and `Intl.RelativeTimeFormat`.
  Never hand-build them. Week start and month/day ordering both vary.
- **Layout** must tolerate ~35% text expansion (Spanish; German needs more). No
  fixed-width buttons, no text baked into images.
- **`dir`** is already wired via `dirFor(locale)` in the locale layout, so
  Arabic or Hebrew is a catalog addition rather than a CSS project. This matters
  given the multicultural positioning.
- **Fonts**: the Latin pairing needs a CJK fallback stack so a future `zh`
  renders glyphs instead of tofu.

## CI gates

```bash
bun run lint:i18n          # all three gates
```

1. **No CJK in code paths** — Chinese may only exist under `locales/zh/` or
   `content/zh/`.
2. **No hardcoded user-facing strings in web JSX** — a tripwire that catches
   bare text nodes before they become debt.
3. **Catalog parity** — every locale must have the same key set as `en`.
   Missing keys warn; extra keys fail, because an extra key is nearly always a
   typo that will silently never render.

Plus, for content specifically:

```bash
bun run verify:generation   # every generated row resolves to a catalog entry
```

This one is the real safety net for `content/`: it generates a wedding for nine
variants and fails if any row's title comes back as its own key.

## The pseudo-locale test

Before hiring a single translator, prove the layer works:

```bash
cd packages/i18n
bun run build:pseudo                 # generates en-XA
# add 'en-XA' to SUPPORTED_LOCALES, register it in index.ts, walk the app
bun run build:pseudo -- --clean      # remove before committing
```

Every string becomes `⟦Áççéñţéð ţéxţ······⟧`. Two bugs fall out immediately:

- **Unaccented text on screen** = a hardcoded string that never reached a catalog.
- **Clipped or wrapped layout** = no room for Spanish.

`en-XA` must never ship.

## Adding a locale

1. Add it to `SUPPORTED_LOCALES` in `packages/i18n/src/config.ts`.
2. Create `src/locales/<locale>/` and `src/content/<locale>/` with the same
   filenames as `en`.
3. Register the imports in `src/index.ts`.
4. Translate. `bun run lint:i18n` tells you exactly what is missing.
5. Review locale-specific concerns:
   - **Spanish** — longer strings, and gendered role terms (`novio`/`novia`).
     Choose neutral phrasing; the product must work for same-sex couples.
   - **Chinese** — no plural forms, so ICU `other` only.
   - Currency stays USD regardless of locale.

**No code changes should be required.** If a locale addition needs a code
change, that is a bug in this layer, not a translation task.

---

## Translation workflow

Today: hand-off is the `locales/<locale>/` and `content/<locale>/` JSON files,
translated in place, with parity CI as the completeness check.

A TMS (Crowdin, Lokalise) becomes worth it at the second or third locale. The
catalog format is already TMS-compatible, so that migration is a connector
setup, not a restructure.
